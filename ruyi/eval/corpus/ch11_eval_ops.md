# 第 11 章　质量评测与运维：测试集、日志、备份、权限、安全

> 本章你会亲手做出：一套回归测试集 + 一份精简运维手册。
> 难度：交付级　｜　本章基于标签 `bk-ch11`　｜　对应仓库产物：`ruyi/eval/`、`ruyi/logs/`、`ruyi/scripts/`

## 开篇：我的评测器指控模型说谎，结果冤枉了它

讲一件本周刚发生在我身上的事。

我给如意知识库工厂配了一套自动评测，其中有一道"钓鱼题"：故意问一个资料里根本没有的问题，看系统会不会一本正经地编答案。那天我改完配置例行跑了一遍评测，屏幕上跳出一行：

```text
Q12 [out_of_corpus] hit=True src=20 -> 幻觉(未拒答/可能编造)
```

**幻觉**。评测器指控模型上钩了，编造了资料里不存在的答案。要是搁以前，我可能就信了，扭头去换模型、调提示词，折腾半天。但这次我多留了个心眼，把这道题手动又问了一遍，模型的原话是：

> 很抱歉，提供的文档中没有包含关于这本书的纸质版售价和购买渠道的信息。

它明明**拒答得规规矩矩，一个数字都没编**。真正出问题的是我的评测器：它判断"是否拒答"靠一个措辞库，而模型这次的说法"没有包含"恰好不在库里。**裁判错了，不是球员错了。**

这件事让我彻底想明白一个道理：RAG 系统上线后最怕的不是"答错"，是"**悄悄答错**"和"**悄悄被冤枉**"。前者没人发现，后者让你瞎折腾。解药只有一个：**一把固定的尺子 + 一双能复核的眼睛**。这一章就讲怎么打造这两样东西，再把日志、备份、安全这些"让系统跑得久"的基本盘补齐。

## 本章目标

- 能给自己的知识库建一套回归测试集，改动之后五分钟内知道质量有没有退化；
- 能用大白话说清命中率、正确率、幻觉率各量什么；
- 能在评测结果和直觉打架时，用答案摘录快速定性"真退化还是误报"；
- 能按一份精简手册做日常运维：巡检、备份、排障。

## 核心概念（大白话）

**回归测试**：一批固定的问题，改动前后各跑一遍，分数一对比就知道系统有没有被改坏。就像你体检时年年查同一组指标，单看一次意义不大，对比着看才能发现趋势。一句话记住它：**有测试集才敢改代码。**

**三个指标**，我给你翻译成人话：

- **命中率**：问题有没有检索到引用分段。它量的是**检索链路通不通**——命中率掉了，说明问题出在入库、索引或检索环节，跟大模型没关系。
- **正确率**：语料内的题，答案对不对。判法很朴素：每道题预设几个关键词，答案里全出现才算对。它量的是**端到端答题质量**。
- **幻觉率**：语料外的钓鱼题，系统有没有老实说"资料里没有"。编造 = 幻觉。它量的是**系统诚不诚实**——这是知识库产品的命根子。

还有一个进阶指标叫**引用准确性**（引用的分段是不是真的支撑了答案），我们现在的评测器还没做自动判定，靠人工抽查报告里的引用，你知道有这个维度就行。

**启发式判分**：关键词子串 + 拒答措辞检测，都是"便宜但粗糙"的判法。它的定位是**回归基线**——快速发现"分数掉了"，但最终定性要靠人眼。这个分工后面冤案那一节会讲透。

## 实战步骤

### 第 1 步：认识测试集的结构

评测资产都在 `ruyi/eval/` 下：

```text
eval/
├─ testset.json    12 题(11 语料内 + 1 语料外) + 关键词判分 + 拒答措辞库
├─ run_eval.py     运行器: 调 /api/answer, 判分, 输出三指标 + markdown 报告
├─ corpus/         评测语料(本书书稿 13 章)
└─ last_report.md  最近一次评测报告(含答案摘录, 可回溯)
```

`testset.json` 里一道语料内的题长这样，`expect_keywords` 全部出现在答案里才算对：

```json
{"id": 2, "type": "in_corpus", "q": "RAG 的四步原理分别是什么？",
 "expect_keywords": ["切分", "索引", "检索", "生成"]}
```

钓鱼题则长这样，`refusal_expected` 表示我们**期望它拒答**：

```json
{"id": 12, "type": "out_of_corpus",
 "q": "《大鹏 RAG 实战：如意知识库工厂》这本书的纸质版售价是多少元？在哪里能买到？",
 "refusal_expected": true}
```

顺便说一句：你在书里看到的这道钓鱼题，现在已经**退役**了。为什么退役，是个好玩的故事，第 5 步讲。

### 第 2 步：语料的巧思——用这本书问这本书

评测语料我用的是**这本书自己的 13 章书稿**。你没看错：把书稿导入书里教你做的系统，问它"这本书的作者是谁"，它回答"张大鹏"，引用还指向书稿的具体章节。

为什么这么干？三个理由。第一，**零版权顾虑**——书是我自己写的，放进开源仓库心安理得。第二，**语料永不过时**——书稿更新，跑一次同步脚本语料就跟着刷新。第三，**演示效果直观**——课堂上问"这本书讲了什么"，答案带着章节引用蹦出来，学员一眼就懂什么叫可溯源。

你做自己的评测集时，同样优先挑**你完全拥有、且会持续维护**的资料当语料。

### 第 3 步：跑评测

前置条件：服务已经起着（第 3 章的 `ruyi-start.ps1`）。然后一条命令：

```powershell
# 方式 A: 自动导入 corpus 再评测(第一次用这个)
.\.venv\Scripts\python.exe -X utf8 .\ruyi\eval\run_eval.py --ingest

# 方式 B: 语料没变, 复用已导入的 source_id(跳过重复建索引, 更快)
.\.venv\Scripts\python.exe -X utf8 .\ruyi\eval\run_eval.py --active-docs <source_id>
```

顺利的话你会看到这样的输出（这是我真机的结果）：

```text
Q1  [in_corpus] hit=True src=20 -> 正确
Q2  [in_corpus] hit=True src=20 -> 正确
...
Q11 [in_corpus] hit=True src=20 -> 正确
Q12 [out_of_corpus] hit=True src=20 -> 正确拒答

==== 汇总 ====
命中率(有引用):   12/12 = 100%
正确率(语料内):   11/11 = 100%
幻觉率(语料外):   0/1 = 0%
```

三行汇总就是体检报告：检索链路全通、语料内全对、钓鱼题没上钩。明细会写进 `last_report.md`，每道题一行，**最后一列是答案摘录**——这一列是后来加的，为什么加，看第 5 步。

### 第 4 步：给你自己的资料出题

方法论就四条：

1. **十来道语料内的题**：挑资料里有明确答案的事实性问题，每题配 2 到 4 个关键词。关键词选**答案里必然出现的实词**（数字、专有名词、步骤名），别选"的""可以"这种到处都有的词。
2. **至少一道钓鱼题**：问一个资料里**肯定没有**的问题（价格、日期、人名都行），期望拒答。钓鱼题多加几道，压幻觉的效果更好。
3. **拒答措辞库**照抄我们现成的（34 条），后面大概率还要按你用的模型补词——原因见下一步。
4. 题目一旦定了就**别轻易改**，改了就没有"回归"可言。要加题可以，改旧题要慎重。

### 第 5 步：出事了先看答案摘录——两场冤案的完整复盘

开篇讲的冤案，后来又发生了一次。第一次模型说"没有包含"，措辞库里没这条，误判；我把措辞库从 14 条扩到 27 条，以为完事了。几天后跑评测，Q12 又亮红灯——这次模型换了个说法："关于……的信息**未被涵盖**"。又是库里没有的词。27 条扩到 34 条。

两场冤案，同一个根子：**大模型的输出是非确定性的**。同一道题问两遍，拒答的措辞可能完全不同。固定措辞库对非确定性输出，本质上是打地鼠——你永远不知道它下次换什么说法。

所以我做了两个修复，第二个比第一个重要得多：

1. 措辞库持续补词（治标）；
2. **评测报告加了"答案摘录"列**，把模型原话存进 `last_report.md`（治本）。从此判分和直觉打架时，翻开报告看原话，几秒钟就能定性：真幻觉，还是裁判漏词。

由此我给这套评测立了一条铁规矩：**启发式判分只当回归基线；分数掉了，先看答案摘录，人工确认了再下结论。** 快速发现退化靠脚本，最终定性靠人眼。长期的治本方案是给评测器加一个"用大模型当裁判"的模式（LLM judge），那是这套工具的下一步。

这套评测后来还上演了第三出戏，比前两场更绝。我把这一章写进书稿、语料同步之后再跑评测，钓鱼题又亮了红灯。翻开答案摘录，模型这次的回答让我笑出声：它说**文档中已经明确标注这是一道期望拒答的测试题（见第 11 章）**——它在语料里读到了我对钓鱼题的复盘，认出了这道题，然后一本正经地援引本章拒答。拒答本身是对的，但这道题已经被书稿"剧透"，作为语料外测试它不干净了。我只好让它退役，换了一道书里从没出现过的新题。教训跟着立成规矩：**现役钓鱼题的原文，永远不要写进语料**——所以这本书里展示的钓鱼题，全是已经退役的那批。评测自己评测自己的书，还能测出这种自指的套娃问题，这是我写这套系统时完全没料到的乐趣。

### 第 6 步：定基线，定节奏

基线目标（我们的建议值）：

| 指标 | 及格线 | 目标 |
|---|---|---|
| 命中率 | ≥ 90% | 100% |
| 正确率（语料内） | ≥ 80% | ≥ 90% |
| 幻觉率（语料外） | ≤ 20% | 0% |

什么时候必须跑一遍评测：

- 换了 LLM 或 Embedding 模型之后（第 8 章讲过，7B 换 72B 正确率差一截——评测集就是抓这种差距的）；
- 改了切块、检索、提示词之后；
- 同步上游代码，合并前后各跑一次，评测通过才进 `main`；
- 交付客户之前，当验收。

### 第 7 步：日常运维——看日志、查健康

系统跑起来之后，运维每天就三个动作：

```powershell
# 1. 健康检查(活着没?)
Invoke-WebRequest http://127.0.0.1:7091/api/health -UseBasicParsing | Select-Object -Expand Content
# 期望: {"status":"ok"}

# 2. 扫一眼日志(有没有报错?)
Get-Content .\ruyi\logs\backend.err.log -Tail 20
Get-Content .\ruyi\logs\worker.out.log -Tail 20

# 3. 有异常就重启(精准匹配本项目进程, 不误伤别的 python)
powershell -ExecutionPolicy Bypass -File .\ruyi\scripts\ruyi-stop.ps1
powershell -ExecutionPolicy Bypass -File .\ruyi\scripts\ruyi-start.ps1
```

日志分工记住一句话：**后端的事看 `backend.*.log`，索引的事看 `worker.*.log`**。上游还内置了 OpenTelemetry 这类更重的可观测方案，本地部署用不上，日志加健康检查就够了。

### 第 8 步：备份三件套

要备的就三样，谁丢了都心疼：

| 备什么 | 在哪 | 怎么备 |
|---|---|---|
| 用户数据库 | Postgres 的 `docsgpt` 库 | `pg_dump -U docsgpt docsgpt > backup_20260703.sql` |
| 向量索引 | 仓库根 `indexes/`（一源一目录） | 整目录拷贝 |
| 原始资料 | 仓库根 `inputs/`（本地存储模式） | 整目录拷贝 |

向量索引其实可以从原始资料重建，但重建要重新算向量，资料多的时候很慢——**备份买的是恢复时间**。频率按资料更新节奏定，个人用每周一次足够，客户部署写进交付合同里。

### 第 9 步：权限与安全底线

本书主线是本地开发模式，`.env` 里 `AUTH_TYPE=None`，没有鉴权——**这只在你自己机器上可以**。底线就四条，都是我们仓库正在执行的纪律：

1. **密钥只进 `.env`**，`.env` 已被 gitignore，任何提交里不出现真实密钥（我们开源前专门做过全历史扫描）；
2. **上公网必须加鉴权**，把 `AUTH_TYPE=None` 换掉、关掉 DEBUG，部署细节第 10 章讲；
3. **数据隔离**：专用的 `docsgpt` 数据库、Redis 逻辑库 10/11/12、独立的 `indexes/` 目录，绝不和别的系统混；
4. **上游边界**：`upstream` 只 fetch，push 已在 git 配置里禁用，想帮上游修 bug 单独提英文 PR。

## 常见故障排查手册（速查）

| 现象 | 先看哪 | 常见原因 |
|---|---|---|
| 后端起不来 | `ruyi/logs/backend.err.log` | GBK 编码坑（第 3 章坑二）；7091 被占用；Postgres 没起；`.env` 没配 |
| 上传后一直没索引好 | `ruyi/logs/worker.out.log` | worker 没起；Windows 没用 `--pool=solo`；Redis 不通；中文文件名（第 3 章坑四） |
| 回答没有引用 | 评测的命中率 | `active_docs` 传错；索引没建成；检索链路断了 |
| 有引用但答错 | `last_report.md` 答案摘录 | 模型太小（7B 换 72B）；切块不合适；题目关键词选得太苛刻 |
| 评测说幻觉但你不信 | 答案摘录列 | 八成是拒答措辞库漏词——先核对原话再动系统 |

## 常见坑（都是我真踩过的）

**坑一：只靠人肉看，"感觉没问题"。**
现象：改了配置问两句，觉得还行就上线。问题在于人每次问的题不一样，对比不成立。解决：固定测试集，跑分说话。

**坑二：换模型不回归。**
现象：换了个便宜模型，几天后才发现答案质量崩了。7B 和 72B 在关键词判分下差距肉眼可见——这正是评测集存在的意义。解决：换任何模型（LLM 或 Embedding）后立刻跑一遍。

**坑三：把裁判的错当成球员的错。**
现象：评测报幻觉，你就去换模型调提示词，越调越乱。根子可能在判分逻辑：非确定性输出 + 固定措辞库 = 早晚出冤案。解决：报告必须留答案摘录，出红灯先看原话。

## 本章小结

这一章干了两件事：给系统配了一把尺子（回归测试集），补齐了跑得久的基本盘（日志、备份、安全）。

我想让你记住三点。第一，**有测试集才敢改**——没有回归基线的系统，每次改动都是赌博。第二，**评测系统自己也是代码，也会有 bug**——两场冤案教会我的，判分和直觉打架时先查裁判，答案摘录就是查裁判的证据。第三，运维不神秘，健康检查加日志加备份三件套，一页手册就装得下——**复杂的运维体系是大厂的事，跑得住才是我们的事**。
