# 第十章 使用 Dify 云端知识库


这一章解决四个问题：
知识库**是什么**、**有什么用**、**什么时候用**、**怎么用**。
前三个问题用大白话讲透，
后面动手实战：界面上搭一遍，再用代码真实跑一遍。




## 一、知识库是什么

大模型很聪明，但它有两个天生的短板：
- 🕰️ 知识有截止日期：训练完成之后发生的事，它一概不知道
- 🔒 不知道你的私有资料：你公司的规章制度、产品手册、内部数据，都不在它的训练数据里

知识库就是给大模型外挂的一个**资料库**：
把你的文档存进去，
大模型回答问题之前先来这里查资料，
查到什么就依据什么回答。

打个比方，没有知识库的大模型是在**闭卷考试**：
全凭训练时记住的东西答题，记错了也只能硬着头皮编。
接上知识库之后就变成了**开卷考试**：
先翻书找到相关段落，再照着书上的内容组织答案，
答得又准又有出处。

这套机制有个专业名字叫 **RAG**（Retrieval-Augmented Generation，检索增强生成），
拆开看就四步：

- 1、切分：把文档按规则切成一个个**分段**（chunk）
- 2、索引：用 Embedding 模型把每个分段转成向量，存进向量数据库
- 3、检索：用户提问时，把问题也转成向量，找出语义最相近的几个分段
- 4、生成：把命中的分段拼进提示词，交给大模型生成最终回答

第八章的本地知识问答助手 Agent，底层走的就是这套流程；
本章的云端知识库同样如此，只是基础设施由 Dify 云端托管。




## 二、知识库有什么用

知识库解决的是"大模型答不准、答不了"的问题，
具体价值有四个：

- 🎯 **治幻觉**：大模型没把握时容易一本正经地编造，有了知识库，答案必须从检索到的资料里来，有据可查，大幅减少胡编乱造
- 🏢 **让大模型懂你的私有知识**：企业制度、产品参数、项目文档这些外界不可能知道的内容，放进知识库就能被准确问答，这是通用大模型永远替代不了的
- 🔄 **知识更新零成本**：业务资料变了，改知识库里的文档就行，立刻生效；不需要重新训练模型，也不用等模型厂商更新版本
- 🔍 **答案可溯源**：Dify 的知识库回答可以标注引用来源，用户能看到答案出自哪份文档哪个分段，出了偏差也方便定位是资料问题还是检索问题




## 三、什么时候该用知识库

不是所有问题都该用知识库解决，
选型前先分清楚三条路的分工：

- 📚 **该用知识库**：让大模型掌握一批会持续更新的私有资料，比如产品手册问答、公司制度查询、课程内容答疑；特征是资料量大、更新频繁、回答要有出处
- 🧠 **该用微调**：想改变模型的说话风格、输出格式、专业口吻，比如让模型永远用某种行文规范写报告；微调教的是"怎么说"，知识库补的是"知道什么"，两者不互相替代
- 📄 **直接塞提示词就行**：资料只有一两份、内容很短且基本不变（比如一页活动规则），直接贴进系统提示词最简单，不必兴师动众建知识库
- 🌐 **该用联网搜索工具**：要的是实时公开信息（今天的新闻、当前的股价、最新的政策原文），这些应该给 Agent 配搜索工具去查，而不是往知识库里存

一句话判断：
**私有的、成规模的、常更新的资料交给知识库；
风格问题交给微调；短小固定的内容直接进提示词；
实时公开信息交给联网搜索。**




## 四、云端知识库和本地知识库的区别

第八章的本地知识问答助手 Agent，
用的是 Ollama 管大模型、Xinference 管 Embedding 模型，
数据全部存在自己的电脑或服务器上。
这一章讲的云端知识库，走的是另一条路：
直接用 Dify 官方云服务（cloud.dify.ai）自带的知识库能力，
Embedding、向量数据库、检索这些都由 Dify 云端托管，不用自己部署。

- 🔐 本地知识库：数据完全私有，适合金融、医疗这类对数据安全要求高的场景，代价是要自己搞定硬件和运维
- ☁️ 云端知识库：开箱即用，注册账号就能建知识库，适合个人学习、内容创作、轻量级团队协作，代价是数据存在 Dify 云端服务器上

两种方式在"知识库怎么用"这个层面是通的：
都是本章开头讲的 RAG 四步（切分、索引、检索、生成），
区别主要在"谁来管基础设施"。

以本课程"大鹏 AI 教育"的云端工作区为例
*（图：Dify 云端知识库文档列表页面，知识库名为"大鹏 AI 教育"）*，
知识库里放了一份示例文档"01 从大模型到 AI Agent.md"，
字符数约 11k，分段模式选的是**通用**，状态显示**可用**，
这就是一个最基础的云端知识库雏形。




## 五、云端知识库的两种搭建方式

打开 Dify 云端工作区，单击顶部导航栏的**知识库**选项，
再单击**创建知识库**按钮，会看到两种搭建方式：

- 🚀 **快速创建**：适合单纯的文档导入场景，上传文件、选分段模式、确认索引方式，几步就能建好知识库，第八章讲的本地知识库配置流程本质上就是这一种
- 🧩 **知识流水线**：适合更复杂、更定制化的场景，能把数据源接入、文档提取、分块处理、索引配置串成一条可视化流水线，还能把这条流水线保存成模板，团队里其他人可以直接复用

本章重点讲**知识流水线**，
这是 Dify 2026 年上线的新能力，也是知识库体系里最值得学的部分；
快速创建的操作和第八章的知识库配置思路是一致的，不再重复讲。




## 六、知识流水线：从数据源到可检索知识库

知识流水线的编排思路是一条流水线：
数据源配置 → 数据处理节点（提取器 + 分块器）→ 知识库节点 → 配置用户输入表单 → 测试并发布。


### 6.1 数据源配置

知识流水线支持 4 种数据源类型：

- 📁 **文件上传**：支持 PDF、Excel、Word 等常见格式，单次最多上传 50 个文件，单个文件不超过 15MB
- 📝 **在线文档**：可以直接接入 Notion 工作空间，把 Notion 页面当作数据源，还能选择是否用提取器转换页面信息
- 🕸️ **网页爬虫**：提供两种引擎，Jina Reader 简洁易用，支持子页面爬取、站点地图、限制爬取页数；Firecrawl 更适合结构复杂的网站，能做深度爬取和批量处理
- ☁️ **在线网盘**：支持 Google Drive、Dropbox、OneDrive 等网盘，自动检索网盘里的文件

对本课程来说，最常用的还是**文件上传**：
把课程里已经美化好的中文版章节 Markdown 文件直接上传，
就能快速搭出一个覆盖全书内容的问答知识库。


### 6.2 数据处理节点：提取器与分块器

数据源接进来之后，要经过两类处理节点。

**文档提取器**（3 种可选）：
- 🔧 Doc Extractor：识别并转换各种文件格式，通用性强
- 🏷️ Dify Extractor：Dify 内置解析器，能连文档里的图片附件一起提取出来
- ⚙️ Unstructured：高度可定制，提供多种提取策略和分块方法，适合有特殊解析需求的场景

**分块器**（3 种类型，对应知识库节点的分段结构）：
- ✂️ 通用分块器：按分隔符（默认换行 `\n`）切分文本，可以自己设置每段最大字符数和重叠长度，最常用
- 🌳 父子分块器：双层结构，子分段负责精确匹配用户提问，父分段提供完整的上下文背景，兼顾检索精度和语义完整性
- ❓ 问答处理器：专门处理 CSV、Excel 这类结构化的问答数据，只需要指定问题列和答案列，适合已经整理好常见问题的场景


### 6.3 知识库节点：分段结构与索引方式

知识库节点决定了文档最终会以什么结构、什么方式被检索到：

- 🧱 通用模式：支持高质量和经济两种索引，索引选项最灵活
- 🌳 父子模式：只支持高质量索引，能保留最完整的上下文，适合技术文档这类需要读懂上下文才能准确回答的内容
- ❓ 问答模式：只支持高质量索引，检索时按问题部分做匹配，命中率高

高质量索引会调用 Embedding 模型把分段转成向量，
支持向量检索、全文检索、混合检索三种方式；
经济模式不调用模型，给每个分段建 10 个关键词的倒排索引，
速度快但语义理解能力弱一些。
如果选用带 Vision 图标的 Embedding 模型，
还能实现图文联合检索，让知识库既能理解文字也能理解图片内容。

⚠️ 有一点要特别注意：分段结构一旦保存发布，就不能再修改了，
建好知识库之前最好先想清楚用哪种模式。


### 6.4 配置用户输入表单

流水线里有些参数（比如某个数据源的 URL、通用分块器的分隔符）
需要让使用者在导入文档时手动填写，这就要靠用户输入表单来实现，
表单字段分两类：

- 🎯 非共享输入：只服务于特定数据源，比如某个网页爬虫节点专用的起始 URL，在对应数据源节点右侧单击"+"按钮添加
- 🌐 全局共享输入：所有节点都能引用的通用参数，比如分隔符、最大分块长度这类配置

支持的字段类型有 7 种：文本、段落、下拉选项、布尔值、数字、单文件、文件列表，
每个字段可以配置变量名称、显示名称、是否必填、默认值、占位符和提示文字。


### 6.5 测试与发布

流水线编排完之后，还有几步收尾工作：

- ✅ 检查完整性：单击右上角的检查清单按钮，系统会标出还没配置完的地方
- 🧪 测试运行：单击 Test Run，一次上传一个文件调试效果，观察分段结果是否符合预期
- 🔍 数据检查：用运行历史查看每次执行的状态，用变量检查功能看每个节点的输入输出数据是否正确
- 🚀 正式发布：确认效果没问题后单击发布，知识库才算正式启用

必须完成知识流水线的配置、调试和发布，才能正式上传文件、
或者让这个知识库被 Agent 应用调用，这一点和普通工作流的发布逻辑是一样的。




## 七、把云端知识库接入 Agent 应用

知识库建好之后，接入方式和第八章讲的本地知识库完全一样：

- 1、在工作室创建一个聊天助手或 Agent 应用
- 2、在应用编排页面的**上下文**部分，单击添加知识库
- 3、勾选刚才建好的云端知识库（比如"大鹏 AI 教育"）
- 4、在调试与预览里提问，验证 Agent 能不能准确引用知识库内容回答

云端知识库同样支持召回测试：
在知识库详情页单击**召回测试**，输入一个模拟问题，
就能直接看到会命中哪些分段、命中分数是多少，
方便在正式接入 Agent 之前，先确认检索效果是否符合预期。
也可以用**元数据**功能给文档打标签（比如按章节、按主题分类），
检索时可以按元数据筛选范围，避免大知识库里检索到不相关的内容。

### 8.3 代码讲解一：客户端骨架与鉴权

所有请求都打到 `https://api.dify.ai/v1`，
鉴权方式是在 HTTP 请求头里带上密钥（Bearer 认证）。
`dify_kb_client.py` 用一个 `requests.Session` 统一挂鉴权头，
后面所有接口共用，不用每次重复写：

```python
@dataclass
class DifyKnowledgeClient:
    api_base: str
    api_key: str

    def __post_init__(self) -> None:
        # 统一挂上鉴权头，后面所有请求共用
        self.session = requests.Session()
        self.session.headers.update({"Authorization": f"Bearer {self.api_key}"})

    def _request(self, method: str, path: str, **kwargs) -> dict:
        url = f"{self.api_base}{path}"
        resp = self.session.request(method, url, timeout=30, **kwargs)
        if resp.status_code >= 400:
            raise RuntimeError(f"Dify API error {resp.status_code}: {resp.text[:500]}")
        return resp.json()
```

这段的要点：
- 🔑 `Authorization: Bearer dataset-xxx` 是唯一的鉴权方式，密钥错了所有接口都返回 401
- 🚨 `_request` 统一处理报错：状态码大于等于 400 就抛异常并带上响应内容，调试时一眼能看到 Dify 返回的具体错误信息（后面踩的 Invalid provider 坑就是这么定位的）


### 8.4 代码讲解二：建库与上传文档

建一个空知识库只需要一个名字：

```python
def create_dataset(self, name: str, permission: str = "only_me") -> dict:
    payload = {"name": name, "permission": permission}
    return self._request("POST", "/datasets", json=payload)
```

往库里上传文档用 `create-by-text` 接口，
把文档内容作为字符串直接传上去：

```python
def create_document_by_text(
    self, dataset_id, name, text,
    indexing_technique="high_quality",
    embedding_model="", embedding_model_provider="",
):
    payload = {
        "name": name,
        "text": text,
        "indexing_technique": indexing_technique,
        # automatic 模式让 Dify 按默认规则分段，等价于界面上的"自动分段与清洗"
        "process_rule": {"mode": "automatic"},
    }
    if embedding_model and embedding_model_provider:
        payload["embedding_model"] = embedding_model
        payload["embedding_model_provider"] = embedding_model_provider
    return self._request(
        "POST", f"/datasets/{dataset_id}/document/create-by-text", json=payload
    )
```

这段的要点：
- 🧱 `indexing_technique` 对应第六节讲的索引方式：`high_quality` 走 Embedding 向量化，`economy` 走关键词倒排索引
- ⚙️ `process_rule` 的 `automatic` 模式等价于界面上的自动分段，也可以换成 `custom` 自定义分隔符和分段长度
- ⚠️ `embedding_model` 两个参数是踩坑后加的：工作区默认 Embedding 供应商没配置时必须显式指定，实测传 `BAAI/bge-m3` 加 `langgenius/siliconflow/siliconflow` 才跑通
- 📬 返回值里有两个重要字段：`document.id` 是文档编号，`batch` 是索引批次号，下一步查进度要用它


### 8.5 代码讲解三：轮询等索引完成

上传接口是异步的：接口返回时文档还没索引完，
Embedding 向量化需要几秒到几十秒。
所以要拿着上一步的 `batch` 批次号轮询进度，
直到状态变成 `completed` 才能做检索：

```python
def wait_for_indexing(self, dataset_id, batch, timeout_seconds=180):
    deadline = time.time() + timeout_seconds
    while time.time() < deadline:
        result = self._request(
            "GET", f"/datasets/{dataset_id}/documents/{batch}/indexing-status"
        )
        data = result.get("data") or []
        if data:
            status = data[0].get("indexing_status")
            if status == "completed":
                return data[0]
            if status == "error":
                raise RuntimeError(f"indexing failed: {data[0]}")
        time.sleep(3)
    raise TimeoutError(f"indexing not completed within {timeout_seconds}s")
```

这段的要点：
- ⏳ 每 3 秒查一次，`completed_segments` 和 `total_segments` 字段能看到"已完成分段数/总分段数"的进度
- 🛑 状态是 `error` 就立刻抛错，别傻等到超时；实测 Invalid provider 那类配置错误就是在这里暴露的


### 8.6 代码讲解四：召回测试

索引完成后就能检索了，
这一步等价于界面上的**召回测试**功能：

```python
def retrieve(self, dataset_id, query, search_method="semantic_search", top_k=3):
    payload = {
        "query": query,
        "retrieval_model": {
            "search_method": search_method,
            "reranking_enable": False,
            "top_k": top_k,
            "score_threshold_enabled": False,
        },
    }
    return self._request("POST", f"/datasets/{dataset_id}/retrieve", json=payload)
```

返回的 `records` 数组里，每条命中记录带两样东西：
`segment.content` 是命中的分段原文，
`score` 是相似度得分（0 到 1，越高越相关）。

这段的要点：
- 🔍 `search_method` 可选 `semantic_search`（向量语义检索）、`full_text_search`（全文检索）、`hybrid_search`（混合检索），对应第六节讲的三种检索方式
- 🎚️ `top_k` 控制返回几条命中；`score_threshold_enabled` 打开后可以设最低分数线，把低相关的命中直接过滤掉
- 🧮 生产环境建议先关阈值观察真实得分分布，再决定阈值设多少

### 8.8 对比实验：知识库的作用一眼看懂

前面测的都是"检索能不能命中"，
这一步才是知识库价值的最终证明：
**同一个模型、同一个问题，接不接知识库，答案天差地别。**

实验设计（代码在 `demo_rag_vs_no_rag.py`）：
- 🅰️ 回合 A：把私有问题直接丢给大模型（Qwen2.5-7B），不给任何资料
- 🅱️ 回合 B：先用 `retrieve` 从知识库检索出相关分段，拼进提示词，再问同一个模型

问题选了一个只有知识库里的文档才知道答案的：
"《大鹏 Dify 开发 AI 智能体》这门课程的主讲老师是谁？由哪个团队出品？"

核心代码就是把检索结果塞进系统提示词：

```python
# 回合 B：先检索知识库，把命中分段拼进提示词再问
records = client.retrieve(dataset_id, QUESTION, top_k=2).get("records", [])
context = "\n---\n".join(
    r.get("segment", {}).get("content", "") for r in records
)
answer_rag = ask_llm(
    llm_key, SYSTEM_RAG.format(context=context), QUESTION, llm_model
)
```

真实运行结果（原样截取，未加工）：

```text
========== Round A: 不接知识库 ==========
您提供的课程名称可能存在一些拼写错误或信息不准确。
正确的课程名称应该是...公司是阿里云开发的一款多模态AI模型。
（随后输出退化成大段重复的乱码，彻底崩坏）

========== Round B: 接知识库（RAG） ==========
[retrieved 2 chunks from knowledge base]
这门课程的主讲老师是张大鹏，由大鹏 AI 教育团队出品。
```

这个对比把第二节讲的知识库价值全部演了一遍：
- 🎯 治幻觉：回合 A 里模型一本正经地编造"阿里云开发的多模态模型"，还越说越乱；回合 B 有据可依，一句话答对
- 🏢 私有知识：课程主讲人这种信息不在任何模型的训练数据里，唯一的知识来源就是我们传进知识库的文档
- 🔍 可溯源：回合 B 的答案能对应到具体命中的分段，答错了也知道去查哪份资料

一句话总结：
**大模型负责"会说话"，知识库负责"说得对"。**


### 8.9 实测踩过的三个坑

- 🔑 **密钥配置要写成"变量名=值"**：只把裸密钥贴进配置文件是读不出来的，程序按变量名取值
- ⚙️ **新建库可能报 Invalid provider**：工作区默认的 Embedding 供应商没配置时，API 新建的库上传文档会报 400 错误；解法是上传时**显式指定 Embedding 模型**（比如硅基流动的 BAAI/bge-m3），模型标识可以先查一个能用的库抄它的配置
- 💡 **界面警告不等于 API 不可用**：工作区界面显示"Embedding 模型不可用"的黄色警告时，已配好模型的库照样能通过 API 正常索引和检索，以实际调用结果为准




## 九、举一反三

云端知识库最适合的场景，是内容更新频繁、
不想自己维护 Embedding 模型和向量数据库的个人开发者或小团队：

- 📚 把整本课程的中文版章节都传进知识库，做一个"课程问答助手"，学员随时提问都能从书里找到准确答案
- 📰 把公司的产品文档、FAQ 定期同步进云端知识库，接一个客服 Agent，减少重复解答的人工成本
- 🔄 用知识流水线的网页爬虫数据源，定时抓取官网文档或博客更新，让知识库始终保持最新，不用每次手动上传

知识流水线能不能保存成模板反复复用，是它和第五节"快速创建"最大的差别；
如果同一类文档需要反复处理（比如每周都有新的会议纪要要入库），
花时间搭一条流水线，比每次手动配置分段规则要省事得多。

最后把本章的主线再串一遍：
知识库是大模型的**外挂资料库**（是什么），
用来治幻觉、装私有知识、随时更新、答案可溯源（有什么用），
私有、成规模、常更新的资料才值得建库（什么时候用），
云端搭建走"快速创建"或"知识流水线"，
建好接入 Agent、做召回测试验证效果（怎么用）。
四个问题想清楚，知识库这个工具就真正用明白了。
